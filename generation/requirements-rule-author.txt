RULE AUTHOR STAGE v2 — candidate design, before execution:
This call authors a reusable rule package, not a finished public problem. It has no tool access and cannot measure the fresh candidate. A repair may include actual Runner evidence for the previous candidate. Produce a complete, executable candidate with a sound algorithm, explicit bounds, witnesses and honest resource estimates. The following stage boundary governs requirementsReview for this call.
1. Assess design fidelity and completeness: all requested mechanics, quantities, objectives and algorithmic interactions must be realized by the contract and code. Report actual missing, weakened or inconsistent requirements as issues and set satisfied=false. Do not claim a feasible design when the algorithm or code is missing.
2. Compilation, validator execution, independent oracle agreement, mutant rejection, reference timing and slow-solution timeout are future Runner qualification obligations. Lack of those not-yet-run measurements alone is NOT an unmet authoring requirement. Mark them as pending verification in authorNotes/complexity/timeLimits.analysis, never invent results. A complete sound candidate can have satisfied=true while those execution checks remain pending; it still cannot activate without passing the unchanged downstream gates. Actual supplied failing Runner evidence must be fixed, not called pending.
3. The performance design target is under two seconds for Java, not a demand to prove measured wall time before execution. Give conservative operation/memory estimates and real maximum-input generators. Five seconds is the pinned qualification wall limit; measured replay/margin checks are performed by the server. No need to certify every possible input's wall-clock runtime. Do not reduce an explicit user bound to avoid testing.
4. Originality applies to the rule design and examples. A fictional title, story, narrative and sample explanations are NOT outputs of this stage and their absence is NOT an unmet requirement. Use neutral entities in all reusable fields; a later presentation stage supplies the setting. Never apply the generic finished-problem storytelling obligation to this package.
5. Separate explicit requirements from unspecified design choices. Explore sound decompositions before giving up: topology, event ordering, how effects are represented and how transitions preserve intermediate visits may be chosen when unspecified, but each choice must be explicit and preserve every requested effect. Never weaken an explicit requirement or claim an arbitrary dynamic graph admits a fixed scalar distance matrix. If no sound complete design is found, state that precise obstruction; lack of measured results alone is not such an obstruction.
6. Difficulty examples are not additional mandatory dimensions or mandatory numeric bounds. Choose unspecified bounds jointly so preprocessing, state transitions and subset DP fit together; preserve explicit user ranges. SIMULATION describes evolving state and event rules and may have a minimum-cost/time objective when requested. EASY does not need a deliberately timing-out slow solution. Repairs retain the original request and all satisfied mechanics and fix concrete failures, rather than perpetuating a false prerequisite for pre-execution measurements or story prose.
