# 생성 문제 검수와 복구

훈련 자동 생성, 태그 생성, 직접 생성, 규칙 기반 생성은 기존 의미·oracle·입력 검증기·논리 오답 검사를 통과한 뒤 같은 자원 검수 단계를 거친다. 기존 작업은 원래 계약을 유지하며, 새 요청에 적용한다.

`resource-profiles-v1.json`은 공통 입력 계약과 30개 유형별 검사 기준이다. 전수검증 기록은 `scripts/normalize-generation-validation.py`로 private provenance를 정리한다. 이전 문제의 인증서가 새 문제의 정답이나 최대 입력을 인증하지 않는다. 답·원본 코드·비공개 테스트를 이 정책 파일에 복사하지 않는다.

## 자원 검수

1. 고정된 명세와 Java 정답·검증기를 저장한다.
2. C++/Python 정답, 일반적인 Java 대안 풀이, 네 가지 최대 입력 생성 계획을 만든다.
3. 별도 모델이 정답 소스와 숨은 답을 받지 않고 최대 입력 생성기의 범위·구조를 검토한다. 모든 선택된 검사 ID를 계획에 포함해야 한다.
4. Runner에서 입력 검증기를 실행하고 세 언어와 Java 대안을 두 번 측정한다. 기존 검증 패키지와 생성 최대 입력을 함께 사용한다. 명령 실행형은 서비스의 동일 언어별 드라이버를 사용한다.
5. 실제 측정값으로 시간·메모리를 정하고 다시 실행한 뒤 게시한다. 메모리 관측 누락은 0이나 추정치로 대체하지 않는다. 동일한 저장 코드·입력 계획을 재측정하며 모델을 다시 호출하지 않는다.

기본 시간은 `max(언어별 하한, ceil((최대 ms × 3 + 1000) / 250) × 0.25)`초이며 하한은 C++ 3초·Java 5초·Python 8초다. 메모리는 실제 cgroup peak의 1.2배에 8MiB를 더해 16MiB 단위로 올린다. 하한 C++ 32MiB·Java 96MiB·Python 48MiB, 상한은 고정 Runner profile이다. 180초 또는 profile 메모리를 넘는 문제는 게시하지 않는다.

새 규칙 기반 문제 인스턴스도 이 GENERAL 정책으로 별도 측정한다. 원래 규칙은행의 시간·느린 풀이 인증 기록은 수정하지 않으며, 그 인증이 새 인스턴스의 완화된 제한에서도 같은 시간 분리를 보장한다고 표시하지 않는다. 논리 오답 WA 검사와 고정 계약 검증은 유지한다. 네 최대 입력과 독립 검토는 제한된 검증 증거이며, 모든 최악 입력이나 가능한 정답 구현의 증명이 아니다.

## 실패 단계별 복구

| 실패 | 복구 범위 | 보존 |
| --- | --- | --- |
| 직접 생성 본문 | 제목·본문만 수정 후 독립 재검수 | 입출력·제약·예제·코드·예비 실행 결과 |
| 태그/규칙 본문·해설 | 본문 관련 산출물과 그에 의존하는 검수 | 고정 규칙·코드·이전 실행 기록 |
| 코드·검증기 | 구현 및 영향을 받는 후속 검사 | 고정 명세·이전 실행·모델 결과 |
| 명세 충돌 | 명세부터 다시 생성 | 이전 계약·산출물·실행·사용량의 감사 기록 |
| 검수/최종 계획 오류 | 해당 검수/계획 단계 | 이전 단계의 통과 결과 |
| 자원 산출물·최대 입력 오류 | 자원 검수 단계만 | 원래 명세·Java 정답·기존 검증 |

직접 생성은 단계별 보완 최대 3회, 전체 최대 6회다. 태그 생성은 새 작업에서 최대 3회 보완한다. 규칙 기반 생성은 역할당 총 3개 시도, 추가 복구 전체 최대 6회이며 실제 API 예산을 새로 예약한다. 자원 검수는 최초 시도와 추가 2회다. 인증/버전/할당량/미상 사용량 timeout, 인프라 오류, fence 오류, 취소·종료·한도 도달은 자동 호출하지 않는다.

실패한 시도의 completion·사용량·실행 submission은 보존한다. 현재 검사 연결만 새 시도로 교체하며, 이전 token의 동일 완료 재전송은 멱등하게 수용하고 다른 결과는 거부한다. 성공한 본문 복구는 계약을 재해석하지 않는다. 훈련은 같은 draft/plan을 이어서 진행하고, 새 유료 요청 키를 만들지 않는다.
