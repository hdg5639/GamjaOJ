# CPU 시간 판정과 테스트 병렬 실행

학습자 요청은 앱 서버 `RUNNER_USER_EXECUTION_MODE=FUNCTIONAL`,
`RUNNER_FUNCTIONAL_SLOTS=5`로 최대 5개 배정한다. 러너의
`GAMJAOJ_FUNCTIONAL_SLOTS=20`은 호스트 슬롯·실제 샌드박스 상한이고,
`GAMJAOJ_TEST_PARALLELISM=4`는 CPU 시간으로 판정하는 정식 제출의
테스트 병렬도다. 컴파일·신뢰된 보조 프로그램도 같은 샌드박스 상한을
공유하므로 요청 수와 테스트 수의 곱이 상한을 우회하지 않는다.

기존 `EXCLUSIVE` 작업은 계속 전체 러너를 독점한다. 조기 중단 계획과
대형 생성 입력은 직렬 처리하고, 작은 생성 테스트의 학습자 실행은 병렬화한다.
결과는 완료 순서가 아니라 계획 순서대로 저장하며 첫 실패 판정도 유지한다.
사용자별 진행 중 요청 3개 제한은 유지한다.

## 측정과 제한

컨트롤러가 cgroup v2 `cpu.stat`의 `usage_usec` 차이를 읽는다. 컨테이너는
신뢰된 대기 프로세스로 유지하고 실제 프로그램은 `docker exec`로 실행하여,
프로그램 종료 직후 cgroup이 사라져 마지막 CPU 카운터를 잃는 일을 방지한다.
컴파일 시간은 별도이며, 실행에는 프로그램·런타임 시작과 실행 래퍼 비용이
포함된다. 최종 CPU 카운터를 읽지 못하면 IE로 처리한다. OOM은
`memory.events`의 `oom_kill` 차이도 확인한다.

`time_limits_json`의 기존 JAVA/CPP/PYTHON 값과 memory는 보존한다.
선택적 `cpu` 객체에 언어별 CPU 제한을 추가하고, 신규 제출의 실행 프로필에
`testCpuSeconds`를 동결한다. UI는 이 경우 CPU 제한과 CPU 실행 시간을 표시한다.
기존 제출·진단 문항의 동결된 프로필은 다시 쓰지 않는다.

CPU 한도와 별도로 벽시계 상한은 `max(기존 벽시계 한도, CPU 한도 × 4 + 2초)`다.
CPU 제한은 약 50ms 간격으로 감시하고 종료 후 최종 카운터로 다시 검사한다.
FUNCTIONAL 학습자 실행에서 TLE가 나거나 한 테스트가 판정 한도의 80% 이상이면
동일 제출을 한 번 EXCLUSIVE로 재배정한다. 최초 증거는 보관하고, 단독 재채점
결과만 최종 확정한다. 기존 wall 프로필에도 이 보호를 적용한다.

## 표본 기반 전환

`scripts/calibrate-cpu-time.py`는 언어 × 일반 입출력/함수형 × 기존 제한의
짧음/김으로 그룹을 나눈다. 각 그룹에서 서로 다른 실행 길이의 문제와 별도
검증 문제를 선택하고, 사용 가능한 비효율 풀이·허용 대체 풀이를 추가한다.
이전 실측 자료에서 느린/메모리 최대 테스트를 골라 같은 입력에서 기존 wall
판정과 CPU 관측을 짝지어 측정한다. 새 CPU 제한은 병렬 부하에서 반복 검증한다.

2026-10-07 표본은 43개 문제의 51개 언어 사례이며 12개 그룹이 검증을 통과했다.
변환은 대부분 `wall × 0.5 + 0.15초`, Java 함수형 긴 제한 그룹은
`wall × 0.5092 + 0.15초`이고 10ms 단위로 올림한다. 이는 기존 검증의 시간
기준 변환이며 전체 최대 입력이나 모든 허용 알고리즘을 새로 증명한 것은 아니다.
표본 밖 문제는 경계 단독 재채점으로 보완한다.

`scripts/stage-cpu-time-limits.py`는 검증된 그룹만 SQL로 준비하며 DB를 수정하지
않는다. 패키지 해시와 이전 제한을 트랜잭션 안에서 검증하고 되돌림 SQL도 만든다.
`scripts/deploy-cpu-time.py`는 DB·환경 백업, 러너 배출, 일치하는 서버/러너 배포,
검증된 SQL 적용을 수행한다. CPU 프로필이 새로 동결된 뒤에는 CPU를 지원하지
않는 옛 러너로 단순히 되돌리지 않는다.

새 문제나 이후 제한 변경은 이 전환 자료를 자동으로 상속하지 않는다.
CPU 제한이 없는 프로필은 기존 wall 판정으로 처리하며 별도 검증 후 전환한다.
실측 자료·정답·숨겨진 입력·배포 SQL은 비공개 운영 디렉터리에 보관한다.
